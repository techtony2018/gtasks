# V0.0.225 — Retry expired proposal read refreshes on demand

## Scope

- System Ticket: `tasks/9f165073-4505-4e11-a473-dccf21e0bfa2`.
- Classification: projection/read-cache freshness repair. No Tony business
  tasks, goals, projects, or proposals are mutated by this release.

## Behavior

When a background read-cache refresh exceeds the bounded refresh window, the
surface still keeps and labels the last verified payload. V0.0.225 changes the
retry contract for explicit forced reads:

- `force=True` reads fence the expired in-flight generation and immediately
  start a replacement refresh.
- ordinary non-force reads still respect the stale/error cooldown and keep the
  last-valid payload without retry loops.
- recent successful payloads still respect the force-refresh cooldown, so normal
  dashboard polling does not fan out extra canonical GBrain reads.

This specifically lets `/api/proposals?refresh=1` recover from a bounded
canonical GBrain timeout without remaining `stale=true` for the full TTL after
the original proposal refresh has already been marked expired.
