# V0.0.226 — Fence expired read refreshes before force cooldown

## Scope

- System Ticket: `tasks/9f165073-4505-4e11-a473-dccf21e0bfa2`.
- Classification: projection/read-cache freshness repair.
- V0.0.225 was pushed and deployed first, but post-deploy polling showed the
  residual condition remained for proposals, tasks, and agent-work surfaces.

## Root cause

The first repair allowed `force=True` reads to retry after an expired background
refresh, but the recent-payload force cooldown ran before the in-flight expiry
check. When a surface had a recent last-valid payload and a stuck background
refresh, `/api/proposals?refresh=1` could keep returning
`refreshing=true/stale=true` because the expired generation was never fenced.

## Behavior

V0.0.226 checks expired in-flight refreshes before applying the recent-payload
cooldown. Explicit forced reads can now:

- fence the stale background generation;
- start a bounded replacement refresh;
- keep serving the last verified payload while the replacement runs.

Ordinary non-force reads still keep the stale/error cooldown and do not create
retry loops.
