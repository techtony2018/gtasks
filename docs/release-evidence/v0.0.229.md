# V0.0.229 — Run explicit read-cache refreshes in the foreground

## Scope

- Direct implementation request from Tony; no System Ticket was created or
  reopened for this repair.
- Classification: read-cache freshness convergence repair.
- No Tony personal tasks, goals, projects, task relationships, proposals, or
  handoff history rows are mutated by this release.

## Root cause

After V0.0.228 was deployed, `/api/tasks?refresh=1`,
`/api/proposals?refresh=1`, and `/api/agent-work?refresh=1` continued to serve
last-valid payloads with `refreshing=true` and `stale=true` beyond the bounded
watchdog window. Direct remote-MCP reads for the same surfaces were bounded, so
canonical data was not corrupt.

The cache issue was process-local: explicit refresh requests still started
background refresh workers. Those workers can be delayed behind foreground
operations and older generations, while the user-facing read state keeps
advertising an in-progress background refresh.

## Behavior

`ReadSurfaceCache.read()` now supports `foreground_refresh=True`. Mission
Control passes that mode only for explicit `refresh=1` reads on:

- `/api/tasks?refresh=1`;
- `/api/proposals?refresh=1`;
- `/api/projects?refresh=1`;
- `/api/agent-work?refresh=1`; and
- `/api/system-tickets?...&refresh=1`.

Normal non-forced reads still use the last-verified background cache behavior.
Explicit refreshes now return the verified fresh payload, or a bounded
stale/error state if the canonical read fails.
